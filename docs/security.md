# セキュリティ設計

## 1. 目標

1. **同じ Wi-Fi に繋がっていても、ペアリングしていない端末（来客・同居人など）は映像を見られない。**
2. **ペアリングできるのは Recorder の画面を見られる人だけ。**（= Recorder の持ち主、またはその許可を得た人）
3. **一度ペアリングすれば、以降はパスワードなしで接続できる。**
4. **Recorder はいつでも Viewer の権限を取り消せる。**

## 2. 基本方針

- パスワード（OTP）は **初回のペアリングにだけ** 使う。
- ペアリング時に、Viewer の **公開鍵** を Recorder に登録する。以降の接続は、Viewer がその秘密鍵で署名できるかどうかで認証する（公開鍵認証）。
- 秘密鍵は端末のセキュアな領域（iOS: Secure Enclave / Android: Keystore）で生成し、**端末の外に出さない**。
- 「誰が接続してよいか」の判断は **Recorder が行う**。サーバーは存在しない。
- 破棄は Recorder の登録リストから公開鍵を消すだけで完結する。
- **LAN 内の TCP 通信（シグナリング）は暗号化されていない前提で設計する。** 秘密情報（OTP そのもの・秘密鍵）は決して流さない。

## 3. ペアリング

### 3.1 OTP

| 項目 | 案 |
| --- | --- |
| 形式 | 数字 6 桁（入力しやすさ優先） |
| 有効期限 | 5 分 |
| 使用回数 | 1 回 |
| 失敗許容回数 | 5 回。超えたら OTP を無効化し、再発行が必要 |
| 生成 | 暗号学的に安全な乱数（iOS: `SecRandomCopyBytes` / Android: `SecureRandom`） |

数字 6 桁は 100 万通りしかないため、**総当たり対策が必須**。サーバーがないので、試行回数の制限は Recorder 自身が行う。

### 3.2 ペアリングの流れ

1. Recorder が OTP を生成して画面に表示し、mDNS の TXT を `pairing=1` にする。
2. Viewer は `pairing=1` の Recorder を一覧に出し、ユーザーが選んで OTP を入力する。
3. Viewer は Recorder に TCP 接続し、自分の公開鍵と **OTP を鍵にした HMAC**（`HMAC-SHA256(OTP, "viewer" || viewerId || viewerPublicKey)`）を送る。**OTP そのものは送らない。**
4. Recorder は HMAC を検証する。正しければ「OTP を知っている Viewer が送ってきた公開鍵」と判断して登録する。間違っていれば失敗回数を数える。
5. Recorder も自分の公開鍵と HMAC（`"recorder" || recorderId || recorderPublicKey`）を返し、Viewer が検証する（相互確認）。
6. OTP を無効化し、TXT を `pairing=0` に戻す。

> なぜ HMAC を付けるのか: 公開鍵だけを送ると、同じ Wi-Fi 上の攻撃者に途中で別の公開鍵にすり替えられても気付けない。OTP を知っている人しか作れない HMAC を付けることで、すり替えを検出できる。
> `"viewer"` / `"recorder"` のラベルを入れるのは、片方向の HMAC をもう片方向に流用されないようにするため。

### 3.3 限界（v1 で受け入れるリスク）

- 数字 6 桁の OTP は、**通信を盗み見て HMAC を手に入れれば一瞬で総当たりできる**（100 万回の HMAC 計算はミリ秒単位）。
  そのため、ペアリングの最中に同じ Wi-Fi 上で **通信を能動的に横取りできる攻撃者**（ARP スプーフィングなど）がいると、中間者攻撃が理論上可能。
- 家庭内ネットワークでこの攻撃が行われる可能性は低く、ペアリングは数分で終わるため、v1 では受け入れる。
- 将来の改善案:
  - **QR コードによるペアリング**: Recorder の公開鍵と十分に長いランダム値を QR で渡せば、この問題は解消する。
  - **PAKE（SPAKE2 など）**: 短いパスワードでも盗聴・中間者に強い鍵交換プロトコル。

## 4. 接続時の認証

1. Viewer は mDNS で、TXT の `id` がペアリング済みの Recorder を見つけて TCP 接続する。
2. Viewer が `viewerId` を指定して接続要求を送る。
3. Recorder は `viewerId` が登録済みか確認する。未登録なら拒否。
4. Recorder はランダムな `nonce` を生成して Viewer に送る（リプレイ攻撃対策）。
5. Viewer は `nonce || recorderId` に秘密鍵で署名して返す。
6. Recorder は登録済みの公開鍵で署名を検証する。
7. 検証に成功した場合のみ、カメラを起動して PeerConnection を作る。

### 4.1 署名方式

- **ECDSA P-256 + SHA-256** を使う。iOS (Secure Enclave) と Android (Keystore) の両方でハードウェア保護付きで使える共通の方式。
- ⚠️ 相互運用の注意点: 署名の表現形式が **DER 形式** と **raw 形式 (r||s, 64 バイト)** の 2 種類ある。
  iOS CryptoKit は両方出力できる（`derRepresentation` / `rawRepresentation`）が、Android の `Signature` API は DER 形式。**どちらかに統一する**こと（DER を推奨）。
- 公開鍵のやり取りも形式を統一する（例: X9.63 非圧縮形式 or SubjectPublicKeyInfo DER）。

### 4.2 SDP への署名（推奨）

4 の認証だけでは、「認証した相手」と「映像の送り先」が同じであることまでは保証できない。
同じ Wi-Fi 上の攻撃者が **偽の Recorder を mDNS で告知** し、Viewer の認証メッセージを本物の Recorder に中継しつつ、SDP だけを自分のものに差し替える、という攻撃が理論上可能。

対策として、**offer は Recorder の秘密鍵で、answer は Viewer の秘密鍵で署名して送る**。
SDP には DTLS のフィンガープリント（`a=fingerprint:`）が含まれるので、署名を検証すれば「ペアリングした相手と暗号化通信している」ことを保証できる。

シグナリングが暗号化されていない LAN 構成では効果が大きいため、v1（M5）で入れたい。

## 5. 破棄

- Recorder の「Viewer 一覧」から削除すると、その Viewer の公開鍵を削除する。
- 接続中であれば、TCP で破棄を通知し、PeerConnection と TCP を即座にクローズする。
- Viewer は破棄通知を受けたとき、または次回の接続時に拒否されたときに、「この Recorder から削除されました」と表示してローカル情報を消す。

## 6. 通信の暗号化

| 通信 | 暗号化 | 備考 |
| --- | --- | --- |
| 映像 | **DTLS-SRTP**（WebRTC が必ず暗号化。無効化できない） | — |
| シグナリング（TCP） | **なし** | 流れるのは公開鍵・HMAC・署名・SDP など、見られても困らない情報だけにする |
| mDNS | なし | TXT に秘密情報を入れない |

> 発展: ペアリング後はお互いの公開鍵を知っているので、それを使って TCP を TLS 化（相互認証）することもできる。実装コストが高いため v1 では 4.2 の SDP 署名で代替する。

## 7. 脅威モデル まとめ

| 攻撃者 | 例 | v1 での対策 |
| --- | --- | --- |
| 同じ Wi-Fi の来客・同居人 | Viewer アプリを入れて Recorder を選ぶ | 公開鍵認証で拒否 |
| OTP 総当たり（オンライン） | ペアリング中に番号を片っ端から試す | 短い有効期限・失敗回数制限（Recorder が管理） |
| LAN 上の盗聴者 | 通信をキャプチャする | 映像は DTLS-SRTP。シグナリングには秘密情報を流さない |
| 偽 Recorder | mDNS で本物と同じ id を告知する | ペアリング時の相互確認、SDP への署名（§4.2） |
| ペアリング中の能動的な中間者 | ARP スプーフィング + OTP のオフライン総当たり | **v1 では受け入れる**（§3.3。QR / PAKE で改善予定） |
| 紛失・譲渡した Viewer 端末 | 端末を拾った人 | Recorder から破棄。秘密鍵は端末外に取り出せない |
| 家の外の第三者 | インターネットから接続を試みる | そもそも外部からの接続経路がない（同一ネットワーク限定） |
