# セキュリティ設計

## 1. 目標

1. **ペアリングしていない人は映像を見られない。**
2. **ペアリングできるのは Recorder の画面を見られる人だけ。**（= Recorder の持ち主、またはその許可を得た人）
3. **一度ペアリングすれば、以降はパスワードなしで接続できる。**
4. **Recorder はいつでも Viewer の権限を取り消せる。**

## 2. 基本方針

- パスワード（OTP）は **初回のペアリングにだけ** 使う。
- ペアリング時に、Viewer の **公開鍵** を Recorder に登録する。以降の接続は、Viewer がその秘密鍵で署名できるかどうかで認証する（公開鍵認証）。
- 秘密鍵は端末のセキュアな領域（iOS: Secure Enclave / Android: Keystore）で生成し、**端末の外に出さない**。
- 「誰が接続してよいか」の判断は **Recorder が行う**。シグナリングサーバーは中継役にすぎない。
- 破棄は Recorder の登録リストから公開鍵を消すだけ。サーバーへの問い合わせは不要。

## 3. ペアリング

### 3.1 OTP

| 項目 | 案 |
| --- | --- |
| 形式 | 数字 6 桁（入力しやすさ優先） |
| 有効期限 | 5 分 |
| 使用回数 | 1 回（成功・失敗にかかわらず、ペアリング要求を受けたら無効化も検討） |
| 生成 | 暗号学的に安全な乱数（iOS: `SecRandomCopyBytes` / Android: `SecureRandom`） |

数字 6 桁は 100 万通りしかないため、**総当たり対策が必須**。

- シグナリングサーバー側で、OTP による検索リクエストにレート制限をかける。
- Recorder 側で、一定回数の検証失敗で OTP を無効化する。
- 有効期限を短くする。

### 3.2 ペアリングの流れ

1. Recorder が OTP を生成し、画面に表示する。
2. Recorder はシグナリングサーバーに「ペアリング待ち」を登録する。登録キーには OTP そのものではなく **OTP から導出した値**（ハッシュ）を使う。
3. Viewer はユーザーが入力した OTP から同じ値を導出し、サーバーで Recorder を探す。
4. Viewer は自分の公開鍵と、**OTP を鍵にした HMAC**（`HMAC(OTP, viewerPublicKey || viewerId)`）を送る。
5. Recorder は HMAC を検証する。正しければ「OTP を知っている Viewer が送ってきた公開鍵」であると判断し、登録する。
6. Recorder も同様に自分の公開鍵と HMAC を返し、Viewer が検証する（相互確認）。
7. OTP を無効化する。

> なぜ HMAC を付けるのか: 公開鍵だけを送ると、途中（例えばシグナリングサーバー）で別の公開鍵にすり替えられても Recorder は気付けない。OTP を知っている人しか作れない HMAC を付けることで、すり替えを検出できる。

### 3.3 限界（v1 で受け入れるリスク）

- 数字 6 桁の OTP は、ハッシュ値が漏れるとオフラインで簡単に総当たりできる。そのため **シグナリングサーバーが悪意を持つケースは v1 では防げない**（ペアリング時の中間者攻撃が理論上可能）。
- 将来の改善案:
  - **QR コードによるペアリング**: 十分に長いランダム値や Recorder の公開鍵そのものを QR で渡せば、この問題は解消する。
  - **PAKE（SPAKE2 など）**: 短いパスワードでも中間者に強い鍵交換プロトコル。

## 4. 接続時の認証

1. Viewer が `recorderId` と `viewerId` を指定して接続要求を送る。
2. Recorder は `viewerId` が登録済みか確認する。未登録なら拒否。
3. Recorder はランダムな `nonce` を生成して Viewer に送る（リプレイ攻撃対策）。
4. Viewer は `nonce || recorderId` に秘密鍵で署名して返す。
5. Recorder は登録済みの公開鍵で署名を検証する。
6. 検証に成功した場合のみ、カメラを起動して PeerConnection を作る。

### 4.1 署名方式

- **ECDSA P-256 + SHA-256** を使う。iOS (Secure Enclave) と Android (Keystore) の両方でハードウェア保護付きで使える共通の方式。
- ⚠️ 相互運用の注意点: 署名の表現形式が **DER 形式** と **raw 形式 (r||s, 64 バイト)** の 2 種類ある。
  iOS CryptoKit は両方出力できる（`derRepresentation` / `rawRepresentation`）が、Android の `Signature` API は DER 形式。**どちらかに統一する**こと（DER を推奨）。
- 公開鍵のやり取りも形式を統一する（例: X9.63 非圧縮形式 or SubjectPublicKeyInfo DER）。

### 4.2 発展: DTLS との結び付け

v1 の方式では、認証（シグナリング経由）と映像の通信路（WebRTC の DTLS）が独立している。
悪意のあるシグナリングサーバーは、認証メッセージだけを正規の Viewer に中継しつつ、SDP を差し替えて自分が映像を受け取る、という攻撃が理論上可能。

対策として、署名対象に **SDP 内の DTLS フィンガープリント**（`a=fingerprint:`）を含めると、認証した相手と映像の送り先が同一であることを保証できる。v2 以降で検討する。

## 5. 破棄

- Recorder の「Viewer 一覧」から削除すると、その Viewer の公開鍵を削除する。
- 接続中であれば、該当する PeerConnection を即座にクローズする。
- Viewer は次回の接続時に拒否され、「この Recorder から削除されました」と表示してローカル情報を消す。

## 6. 通信の暗号化

- 映像: WebRTC が必ず **DTLS-SRTP** で暗号化する（無効化できない）。TURN で中継される場合も暗号化されたまま。
- シグナリング: **WSS (TLS)** など暗号化された通信路を使う。

## 7. 脅威モデル まとめ

| 攻撃者 | 例 | v1 での対策 |
| --- | --- | --- |
| 無関係の第三者 | Recorder の ID を知っている人 | 公開鍵認証で拒否 |
| OTP 総当たり | ペアリング中に番号を片っ端から試す | 短い有効期限・レート制限・失敗回数制限 |
| 盗聴者 | 同じ Wi-Fi にいる人 | DTLS-SRTP / TLS で暗号化 |
| 紛失した Viewer 端末 | 端末を拾った人 | Recorder から破棄。秘密鍵は端末外に取り出せない |
| 悪意あるシグナリングサーバー | サーバー運営者・乗っ取り | **v1 では対象外**（§3.3, §4.2 の改善案で対応予定） |
